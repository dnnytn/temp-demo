01 What is SOPS?

SOPS (Secrets OPerationS) is an open-source tool, originally from Mozilla and now maintained under the getsops organization, for encrypting and decrypting values inside structured files — YAML, JSON, ENV, INI, and plain binary.

The key idea is that SOPS encrypts values, not the whole file. Keys, structure, and comments stay in plaintext. That single design choice is why a file encrypted with SOPS still looks like a YAML or JSON file, still diffs sensibly in git, and can still be validated by schema tools — it just has ciphertext where the secret values used to be.

SOPS itself doesn't do any cryptography — it delegates that to a key management backend: a cloud KMS (AWS KMS, GCP KMS, Azure Key Vault), HashiCorp Vault, PGP, or age. This repo uses age.

02 What is age?

age (“actually good encryption”) is a modern, simple file encryption tool created by Filippo Valsorda, designed as a smaller, harder-to-misuse alternative to PGP/GPG for this exact use case: encrypting a file to a recipient's public key.

An age key pair

  • Public key (recipient): age1d99kgmr6fd76fzck9pz0xv6vtfzzksemsl4ztz62pmtvwska4dfqlmlgfg
  • Private key (identity): AGE-SECRET-KEY-1QYA46XR37...

Under the hood

  • X25519 (Curve25519 Diffie-Hellman) for the key exchange
  • ChaCha20-Poly1305 for authenticated encryption of the content
  • No keyservers, no web of trust, no key expiry dates to manage

That's the whole key model: one public key you can hand out freely to encrypt to you, one private key you keep secret to decrypt. No GPG keyring, no trust levels, no multi-megabyte key files.

03 The problem this solves

Every team ends up needing to answer: where do our secrets live? The usual answers all have a gap:

Plaintext in git

  • Anyone with repo/clone access has every secret, forever, in history
  • Revoking access doesn't revoke exposure — the secret is already out
  • Deleting the file doesn't remove it from git history

.env kept out of git

  • No version history, no diff, no code review on secret changes
  • Distributed by Slack/email/AirDrop — each hop is a leak surface
  • Easy for one environment to silently drift from another

A separate secrets vault only

  • Extra infrastructure to run, patch, and back up
  • Secrets are disconnected from the code/config that uses them
  • Still need a bootstrapping secret to authenticate to the vault itself

SOPS + age

  • Secrets live next to the config that uses them, version-controlled
  • Every change to a secret goes through normal git history / PR review
  • No extra service to run — just a CLI and a key pair

In short: teams want secrets to be versioned, reviewable, and colocated with the config that consumes them, without handing plaintext credentials to everyone who can read the repository.

04 Why this is more secure than “just encrypt the file”

It's tempting to think "encryption is encryption" — just gpg -c or openssl enc the whole file with a passphrase and commit that. SOPS + age is a meaningfully different, stronger model:

Ad-hoc symmetric encryptionSOPS + age
Key distribution A shared passphrase has to reach every team member out-of-band — itself a leak risk, and it's the same secret for everyone Asymmetric: hand out the public key freely. Anyone can encrypt to a recipient without ever holding the thing that decrypts it
Multiple recipients Everyone shares one passphrase — revoking one person means rotating and redistributing to everyone SOPS can encrypt the same file's data key to several age/KMS recipients independently — remove one recipient without touching the others' access
What's readable in a diff The whole file is one opaque blob — git diff shows nothing useful Only values are ciphertext; structure, keys, and comments stay readable, so reviewers can see which secret changed
Tamper detection Usually none — a corrupted or edited blob may decrypt to garbage silently SOPS stores a MAC over the whole document; any change to keys/values/structure without re-encrypting is detected on decrypt
Rotation Re-encrypt and redistribute the new passphrase to every human by hand sops rotate / sops updatekeys re-wraps the data key for new recipients without needing a shared secret handoff

The core reason this is stronger isn't a "better cipher" — ChaCha20-Poly1305 and AES-GCM are both fine. It's that the key management problem is solved correctly: asymmetric keys mean encrypting never requires possessing the secret that decrypts, and per-recipient wrapping means access can be granted or revoked per person without a global secret rotation.

05 Why the ciphertext is safe to commit to git

Committing the output of SOPS is safe for the same reason it's safe to publish a TLS certificate's ciphertext on the wire: what's stored is not the secret, it's data that is computationally infeasible to reverse without one of the matching private keys.

Plaintext value
e.g. a database password
→
Data key
random per-file key, generated once
→
AES256-GCM
encrypts each value with the data key
→
age wraps the data key
to each recipient's public key
→
Committed to git
only ciphertext + wrapped data key

What actually lands in the repo is:

  • Each secret value, individually encrypted (visible as ENC[AES256_GCM,...])
  • A per-file data key, itself encrypted (“wrapped”) to every configured age recipient's public key
  • A MAC over the document so any tampering is detectable

None of that is reversible without an age private key matching one of the recipients — and the private key never goes into the repo (it's gitignored in this POC, exactly like a private key should be). Someone who clones the repo gets the ciphertext and the public key it's addressed to; they cannot decrypt anything with only those two things, any more than they could decrypt HTTPS traffic just by watching it.

The threat model this doesn't cover: if the private key itself leaks (e.g. someone accidentally commits keys/age-key.txt), the secrets encrypted to it are compromised, same as any key-based system. That's why the private key is the one thing in this workflow that must never be checked in.

06 Walkthrough: encrypting and decrypting

This walks through the exact files in this repo: .sops.yaml and examples/secrets.yaml.

0. Prerequisites

# age & sops CLIs on your machine
age --version
sops --version
Step 1 Generate an age key pair

This produces both keys as one file — the comment lines contain the public key, the last line is the private key.

age-keygen -o keys/age-key.txt
# created: 2026-07-27T10:44:45Z
# public key: age1d99kgmr6fd76fzck9pz0xv6vtfzzksemsl4ztz62pmtvwska4dfqlmlgfg
AGE-SECRET-KEY-1QYA46XR37MVS30CD2TAKNE08V5JHLYEMNXGQFSANW43MSU6UYQCSFJMRU4

keys/age-key.txt is gitignored — it never gets committed.

Step 2 Point .sops.yaml at the public key

This is the only place the public key needs to live, and it's safe to commit — it tells SOPS which recipient(s) new files under examples/ should be encrypted to.

keys:
  - &poc_age age1d99kgmr6fd76fzck9pz0xv6vtfzzksemsl4ztz62pmtvwska4dfqlmlgfg

creation_rules:
  - path_regex: examples/.*\.yaml$
    age: *poc_age
  - path_regex: examples/.*\.json$
    age: *poc_age
  - path_regex: examples/.*\.env$
    age: *poc_age
Step 3 Write the secret as plain YAML
# examples/secrets.yaml, before encryption
database:
  host: db.internal.example.com
  username: app_user
  password: correct-horse-battery-staple
api:
  stripe_key: sk_test_51NfakeKeyForDemoPurposesOnly
  jwt_secret: super-secret-jwt-signing-key
Step 4 Encrypt it in place
sops -e -i examples/secrets.yaml

SOPS reads .sops.yaml, matches the path against path_regex, generates a random data key, encrypts each value, wraps the data key to poc_age, and rewrites the file:

database:
    host: ENC[AES256_GCM,data:7Bb5fPaCmut2yv7Q96yqiXwVlWHPa9k=,iv:NoAAK3q...,tag:ggiWAWiR5CtCjdTUfZnuuA==,type:str]
    username: ENC[AES256_GCM,data:nGRsFVO6kG4=,iv:c3dXiEZwDwPTjghW...,tag:QeoCG5uaYlytjTNr+fL3xw==,type:str]
    password: ENC[AES256_GCM,data:hnQ/n3cEmupJ2i5wLOZgj/1oQwMhbxJIkPUQ+Q==,iv:Ctm1c5vdcTJWBTH8E4f2...,tag:GcASDFvFnRijGdLXZPISxA==,type:str]
api:
    stripe_key: ENC[AES256_GCM,data:VGqiKnIioNwhpHKkc52znQ5F+lgWxU43NdX0dNhkTeILMLm8VQ==,iv:f1C6N8pBW7Au...,tag:Y0cSkDbDDDytwW36genfSg==,type:str]
    jwt_secret: ENC[AES256_GCM,data:/UzFipC4rxr4X3P5lFX3tJQ/FbqrsPgsidgAfw==,iv:a3RdGanZQjQsUAJJ...,tag:vW+3H63q0jDwuMvcY5ROjg==,type:str]
sops:
    age:
        - recipient: age1d99kgmr6fd76fzck9pz0xv6vtfzzksemsl4ztz62pmtvwska4dfqlmlgfg
          enc: |
            -----BEGIN AGE ENCRYPTED FILE-----
            ...
            -----END AGE ENCRYPTED FILE-----
    mac: ENC[AES256_GCM,data:qWdabEl5xDZL5jFOZsfUDsbtLZAaYk8Fd2tz2mDEeVTG0Xd...,type:str]
    version: 3.9.4

This is exactly what's checked into examples/secrets.yaml in this repo — note the top-level keys (database, api, host, password, ...) are still plaintext, only the values changed.

Step 5 Decrypt it

Point SOPS at your private key file, then decrypt to stdout:

export SOPS_AGE_KEY_FILE=$(pwd)/keys/age-key.txt
sops -d examples/secrets.yaml
database:
    host: db.internal.example.com
    username: app_user
    password: correct-horse-battery-staple
api:
    stripe_key: sk_test_51NfakeKeyForDemoPurposesOnly
    jwt_secret: super-secret-jwt-signing-key

SOPS unwraps the data key using your age private key, verifies the MAC (detecting any tampering), then decrypts each value back to plaintext.

Step 6 Edit a secret without ever seeing a diff of ciphertext noise
sops examples/secrets.yaml

This decrypts the file into a temp buffer, opens it in $EDITOR, and re-encrypts on save — you edit plaintext, the file on disk stays ciphertext.

Step 7 Add or rotate recipients
# add a teammate's public key to .sops.yaml, then:
sops updatekeys examples/secrets.yaml

# or rotate the data key without changing who can decrypt:
sops -r -i examples/secrets.yaml

updatekeys re-wraps the existing data key to the new recipient set — no need to know the plaintext or coordinate a passphrase handoff with anyone.

See README.md for the same commands applied to the examples/secrets.json and examples/secrets.env variants in this repo.
